# スキル運用マニュアル

`AGENTS.md` と `skills/`（14スキル）を実際に使うための手順書。
「なぜ必要か」から具体的な使い方・保守・トラブル対応まで、例を中心にまとめる。

---

## 1. なぜこの仕組みが必要か

### 解決したい問題

普通にClaudeへ頼むと、毎回ゼロから、汎用的な優等生として答える。
深い作業（デバッグ・研究・執筆）でも「なんとなく上手い素人」で止まり、
プロが必ず踏む手順を飛ばしてしまう。例えば——

- バグ修正で、原因を特定せず当てずっぽうで直す → 再発する
- 研究提案を、一つの視点だけで褒めて終わる → 弱点を見逃す
- 文書を、読者を意識せずいきなり書き出す → 伝わらない

### 3つの部品がどう効くか

| 部品 | 役割（たとえ） | 無いとどうなる |
|---|---|---|
| `skills/`（14個） | プロの手順書のストック | Claudeが素人判断で動く |
| `AGENTS.md` | 受付係・司令塔（どの手順書を開くか） | 手順書があっても選び間違える |
| `CLAUDE.md` の `@AGENTS.md` | 配線（司令塔を繋ぐ1行） | 司令塔が存在しないのと同じ |

### 具体例：「この関数、たまに落ちるから直して」

**仕組みが無い場合**
> コードを眺めて「たぶんここ」と1行直す。動いたように見えて、また落ちる。

**仕組みが有る場合**
> AGENTS.md が `debugging-methodology` を起動 →
> ① 落ちる状況を再現できる手順を作る →
> ② 仮説を立てて実験で検証 →
> ③ 原因の因果連鎖（引き金→仕組み→症状）を特定してから直す →
> ④ 修正後にもう一度再現テストして再発しないことを確認。

要するに **「Claudeを毎回プロの水準に底上げする仕組み」**。これが全体の目的。

## 2. 全体像と配置

3つの部品はこう繋がる。

```
.claude/
├── CLAUDE.md          # Claudeが最初に読む。@AGENTS.md で司令塔を繋ぐ
├── AGENTS.md          # 司令塔：どの場面でどのスキルを使うかの振り分け表
└── skills/
    ├── claude-fable/SKILL.md
    ├── debugging-methodology/SKILL.md
    └── ...（全14スキル）
```

置き場所は用途で選ぶ。

- **個人用（全プロジェクトで使う）** → `~/.claude/`
- **プロジェクト用（そのリポジトリ限定・チーム共有）** → `<リポジトリ>/.claude/`（git に入る）

---

## 3. 初回セットアップ（この通りにやる）

**手順1：フォルダを置く**
`skills/` フォルダと `AGENTS.md` を、選んだ `.claude/` の直下にコピーする。

```bash
# 例：個人用に入れる場合
mkdir -p ~/.claude
cp -r skills ~/.claude/
cp AGENTS.md ~/.claude/
```

**手順2：CLAUDE.md から繋ぐ**
`~/.claude/CLAUDE.md`（無ければ新規作成）に、通常のテキスト行として1行足す。

```markdown
@AGENTS.md
```

> 注意：`@` はコードブロックの中や `` `@AGENTS.md` `` のようなインラインコードだと
> import として無効になる。普通の行に書くこと。

**手順3：正しく置けたか確認**

```bash
cd ~/.claude/skills
# 各フォルダに SKILL.md があり、name がフォルダ名と一致するか
for d in */; do
  n="${d%/}"
  fn=$(awk '/^name:/{print $2; exit}' "$d/SKILL.md")
  [ -f "$d/SKILL.md" ] || echo "SKILL.md 無し: $d"
  [ "$fn" = "$n" ] || echo "名前不一致: $d (name=$fn)"
done
# name の重複検出（あるとトリガーが競合する）
grep -h '^name:' */SKILL.md | sort | uniq -d
```

何も出力されなければ正常。

## 4. 日常の使い方（具体的に）

基本は **普通に日本語で頼むだけ**。AGENTS.md の振り分けに従い、Claudeが自動でスキルを選ぶ。

### ケース別の実際の動き

**ケースA：「このコードのバグを直して」**
→ `senior-software-engineering` を土台に、原因究明で `debugging-methodology` が起動。
納品前に「敵対的な自己レビュー」として `review-methodology` が走る。

**ケースB：「この研究テーマ、筋がいいか見て」**
→ `research-advisor` が起動し、新規性・実現可能性・文献ギャップの観点で評価。
多視点で叩いてほしいなら「委員会でレビューして」と足すと `research-committee` が動く。

**ケースC：「この内容で報告書を書いて」**
→ `professional-writing-workflow` が起動。読者分析→構成→推敲の順で進み、
事実確認が要る箇所で `expert-research-methodology`、最後に `review-methodology`。

**ケースD：「線形代数を基礎から教えて」**
→ 成果物ではなく学習が目的なので `deep-learning-tutor` が起動。
答えを渡さず、理解度確認→段階的な演習→ヒント先出しで進める。

### 使わせ方を強制したいとき

Claudeが選び違えたら、依頼文でスキル名を直接指定する。

> 「`debugging-methodology` に従って、この落ちる関数を調べて」
> 「行き詰まってるので `hard-task-operating-procedure` で立て直して」

## 5. スキルの追加・変更・削除（実例つき）

### 追加する

**手順1：** `skills/<新スキル名>/SKILL.md` を作る。中身の骨格：

```markdown
---
name: code-review-checklist
description: >-
  プルリクエストのレビュー時に読み込む。差分の論理誤り・抜け・
  セキュリティ懸念・命名の一貫性を点検し、指摘を優先度順に整理する。
  トリガー：PR, コードレビュー, 差分レビュー, マージ前チェック。
---

# Code Review Checklist

## 目的
（このスキルが何をどう進めるか本文を書く）

## 手順
1. ...
2. ...
```

**手順2：** AGENTS.md の「タスク種別 → 使うスキル」表に1行足す。

```markdown
| PR の差分をレビューする | `code-review-checklist` |
```

役割が既存スキルと近いなら、「紛らわしいスキルの使い分け」にも一言書く。

### 変更する

- SKILL.md 本文を直接編集する。
- `name` を変えたら、**フォルダ名も同じ名前に変える**（一致必須）。

### 削除する

- フォルダごと消す。
- **AGENTS.md の該当行も必ず消す**（残すと表と実体がずれる）。

> **最重要：description が発動精度を決める。**
> 「何をするスキルか」ではなく「**どんな状況で開くべきか**」を、
> 具体的なトリガー語（例：バグ, レビュー, 調査, 教えて）とともに書く。
> ここが曖昧だと、必要な時に動かない／不要な時に動く。

## 6. 保守（月1くらいで見直す）

チェック項目：

- **name の重複** — 同じ `name` が2つあるとトリガーが競合する。`uniq -d` で検出。
- **役割の重なり** — 近い役割のスキルが増えたら統合するか、AGENTS.md で使い分けを明記。
  現状の要注意ペア：`hard-task-operating-procedure` と `hard-task-metacognition`、
  研究系の `research-advisor` / `research-committee` / `phd-advisory-committee`。
- **コピー残骸** — `*-copy` のような複製を残さない。
- **表と実体の整合** — AGENTS.md の表に載っているスキルが、実際に `skills/` にあるか。

一括チェックは 3節の確認コマンドを再利用する。

---

## 7. トラブルシューティング

| 症状 | 主な原因 | 対処 |
|---|---|---|
| スキルが全く発動しない | 置き場所が違う／ファイル名が `SKILL.md` でない | `.claude/skills/<name>/SKILL.md` の形か確認 |
| 意図しないスキルが動く | `description` が広すぎ／トリガー語が曖昧 | description を絞り、開くべき状況を具体化 |
| 似たスキルが競合する | 役割の重複・`name` 重複 | 統合するか AGENTS.md で使い分けを明示 |
| AGENTS.md が効かない | CLAUDE.md に `@AGENTS.md` が無い／パスがずれ | import 行とパス（相対パス）を確認 |
| import が反映されない | コードブロック内に `@` を書いた | 普通のテキスト行に書く |

---

## 8. 運用のコツ（3つだけ覚える）

1. **claude-fable を常に外枠に。** 個別スキルはその中で選ぶ。土台の思考規律が全体の質を決める。
2. **description に投資する。** 発動するかしないかは説明文でほぼ決まる。困ったらまずここを疑う。
3. **AGENTS.md と skills/ を同期。** スキルを足し引きしたら、必ず AGENTS.md の表も直す。
